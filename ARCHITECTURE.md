# Task & Issue Tracking architecture

## Repository inspection and current implementation

The repository was empty before the documentation setup. Initial inspection found no application stack or conventions. The user then authorized a working local-storage mockup. The following stack was established for that implementation without installing external packages.

| Area | Detected technology or convention |
| --- | --- |
| Language | HTML, CSS, JavaScript; CommonJS for Node scripts/tests |
| Frontend/framework | Browser DOM APIs; no frontend framework or build step |
| Styling/UI components | `src/styles.css` with shared CSS variables, responsive task rows, shared task form, native dialogs |
| Backend | No application backend; `server.cjs` serves only allowlisted static assets on loopback |

| Testing | Node's built-in `node:test` and `node:assert/strict`; `npm test` |

The root governance files and six agents under `.kilo/agent/` remain in place. `kilo.json` preserves the user's exact supplied value.

## Separation of concerns

For an implementation with a backend, use this responsibility chain:

`UI / Page / Component` -> `Service / API Client` -> `Backend Controller` -> `Business Logic / Service` -> `Repository / Database`

- UI pages and components render state, collect inputs, and invoke service operations. Shared inputs, task displays, and confirmation dialogs should be reused.
- The service/API client owns transport, request/response mapping, and normalized errors. Components must not contain raw fetch calls or direct database access.
- Backend controllers validate request schemas, invoke business services, and translate results into the established public API contract.
- Business services enforce task rules, status transitions, and timestamp ownership.
- Repositories isolate persistence queries and mapping from business logic.

For a frontend-only or mock implementation, adapt the chain to:

`UI / Page / Component` -> `Task Service / API Client` -> `Mock Adapter / Repository`

The mockup implements `src/app.js` -> `TaskService` -> the local-storage adapter in `src/task-service.js`. The adapter obtains browser storage; presentation code never reads or writes storage directly. The service offers `list(query)`, `get(id)`, `create(input)`, `update(id, input)`, `setStatus(id, status)`, and `remove(id)`. It is synchronous because all operations are local. UI mutation controls show pending state before calling the service. A future backend adapter can preserve these responsibilities while introducing asynchronous transport.

`list` supports `search`, `status`, `priority`, `assignee`, `unassigned`, `sort`, and a `view` (`all`, `completed`, `upcoming`). Upcoming queries include `today` and `until` as calendar dates. Sorting supports `newest`, `due`, `priority`, and `title`, with identifier ordering as a stable tie breaker. Tasks without a due date sort last for due-date sorting.

## Target data model: Task

Tasks represent the tracking unit for both task and issue workflows; a separate issue model is not defined by this setup.

| Field | Target representation and rules |
| --- | --- |
| `id` | Stable, unique opaque identifier generated by the service/persistence boundary; immutable after creation |
| `title` | Required string; reject blank or whitespace-only values |
| `description` | String for task details; may be empty |
| `priority` | Enum: `Low`, `Medium`, `High`, `Urgent` |
| `status` | Enum: `Todo`, `In Progress`, `Under Review`, `Done` |
| `assignee` | Name or email string; nullable when unassigned; no user directory currently exists |
| `dueDate` | Nullable calendar date in `YYYY-MM-DD` format; validate actual calendar dates |
| `createdAt` | ISO 8601 UTC timestamp set at creation by the service/backend; immutable |
| `updatedAt` | ISO 8601 UTC timestamp maintained by the service/backend on successful mutations |

The shared schema trims title/description/assignee; title accepts 1–160 characters, description up to 5,000, and assignee up to 120. Blank assignees and due dates become `null`. Forms default to `Medium` priority and `Todo` status. Any transition between the four valid statuses is permitted, including reopening a completed task to `Todo`. An assignee may be a name or email; there is no directory or email-only restriction.

Due dates are calendar dates, displayed without UTC day shifts. Creation/update timestamps are stored in UTC and displayed in the browser's locale/timezone. The service controls identifiers and timestamps and ignores attempts to overwrite them. Each mutation reads the latest saved array before writing. Concurrent tabs use last-write-wins; the UI refreshes on storage events and preserves open form input. This is a single-browser mockup, with no multi-user synchronization or backend concurrency guarantees.

Six sample tasks are seeded only when the storage key is absent. An existing empty array stays empty. Failed storage writes do not produce a success message or remove a task from the list; malformed stored data is reported without overwriting it.

## Core feature flows

1. **List, sort, and filter:** A page sends query parameters to the task service and renders the returned tasks. Support sorting by documented task fields and filtering by status, priority, and assignee, including unassigned tasks. Define stable ordering and keep filters active after mutations.
2. **Search:** Pass title/description search through the same service query contract. Combine search with filters and sorting. Distinguish an empty repository from a search with no matching results.
3. **Details:** Load a task by `id` through the service. Handle loading, successful display, missing/deleted tasks, and retrieval errors.
4. **Create:** Collect task inputs using shared form controls, validate against the shared schema, submit through the service, and show the created task or refresh the relevant list after success. Preserve entered values if submission fails.
5. **Edit:** Load the current task, reuse the form and schema, and submit editable fields through the service. Preserve the identifier and creation timestamp. Document concurrency handling when persistence is established.
6. **Quick status transitions:** Submit a status change through the service and enforce the documented transition policy there. Prevent duplicate submissions while pending. If optimistic UI is used, restore the previous status on failure.
7. **Delete:** Open a reusable confirmation modal/dialog identifying the task. Cancellation performs no deletion. Only explicit confirmation invokes the service delete operation; show pending state and report success or failure without silently removing a failed deletion.

These flows are implemented by the mockup through the service methods described above. The list retains search and filter selections after mutations. Task details and the shared create/edit form use a side-panel dialog; deletion has a separate confirmation dialog with a safe cancellation action. No backend endpoints are implied.

## Mandatory UI states

- **Loading:** Show a meaningful progress indicator during initial retrieval and pending mutations; prevent duplicate submissions.
- **Empty:** Explain when no tasks exist, offer creation where appropriate, and provide filter/search recovery when there are no matches.
- **Success:** Render loaded data and provide clear confirmation of successful creation, editing, status changes, and deletion.
- **Error:** Give understandable field or operation errors and a retry/recovery action where appropriate. Preserve usable task data and form values.

## Validation and error flow

`Input` -> `Shared schema validation` -> `Service boundary validation` -> `Backend validation, if present` -> `Business rules` -> `Persistence` -> `Normalized result/error` -> `UI feedback`

Validate required fields, types, enum membership, identifiers, dates, and protected fields. Once limits and transitions are established, enforce them consistently. Reject invalid input before persistence; server-side validation remains authoritative when a backend exists. Map validation failures to field messages and normalize missing tasks, unavailable services, and persistence failures into clear operation errors. Log diagnostic detail only in an appropriate diagnostic context and exclude credentials and sensitive payloads from user-facing messages.

## Testing expectations

The native service tests run with `npm test` or `node --test tests/*.test.cjs`. Cover CRUD persistence, protected fields, search/filter/sort combinations, status transitions, schema boundaries, failed storage operations, and corrupt-data preservation. Browser checks should exercise shared-form validation, deletion cancellation/confirmation, persistence after reload, empty/error states, keyboard access, and mobile layout. Record real commands and results; do not report unexecuted checks as passing.
